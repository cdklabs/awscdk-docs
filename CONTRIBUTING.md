# Contributing to CDK Docs

## Getting Started

The main way to contribute is to **open an issue**: describe the outcome you want, the constraints, and how to tell it is done. Agents pick issues up from there — they implement, open the pull request, and respond to review. You don't need a local checkout to contribute this way.

## How We Work

This project follows an agent-driven development workflow. Humans define *what* to build; agents handle the *how*.

### Roles

| Role | Responsibility |
|------|---------------|
| Human | Write issues as specs, review PRs, approve and merge |
| Agent | Implement issues, create PRs, respond to review feedback |

### Workflow

1. **Humans write issues as specs** — Issues describe the desired outcome, constraints, and acceptance criteria. Humans don't write code directly.
2. **Agents implement** — Agents pick up issues, create feature branches, and open pull requests.
3. **Review is collaborative** — Both agents and humans review PRs. Agents can suggest improvements; humans can request changes.
4. **Only humans merge** — Approval authority belongs exclusively to humans. Once approved, GitHub auto-merge (armed by the `auto-queue` workflow) merges the PR when the required checks pass.

## Local Development

To run the site yourself:

Prerequisites: Node.js 22+

```bash
# Install dependencies
npm ci

# Start docs dev server with hot reload
npx projen docs:dev

# Build the full site for production (sharded — the single-process
# docs:build does not scale to the full API surface)
npx projen docs:build:sharded

# Preview production build locally
npx projen docs:preview
```

## Implementation Conventions

### Branch Naming

Use the format: `type/author/short-description`

Examples:
- `feat/stacks/add-search`
- `fix/agent/broken-nav-links`

### Commits

Write clear, conventional commit messages:
- `feat: add module search`
- `fix: correct link resolution for Python docs`
- `docs: add ADR for static site generator choice`

### Pull Requests

- Reference the issue with `Closes #N` in the PR description.
- Keep the PR focused on a single issue.
- Provide a short summary of what changed and why.

### Code Quality

- All code must be covered by tests. PRs without adequate test coverage will be rejected.
- Tests assert on the produced output — rendered pages, built assets, files as generated by `npx projen` — not on configuration source. The exception is a property that has no runtime output to express it (action pinning, secret handling, a no-interpolation rule in a workflow `run:` block): such a test is legitimate and carries a one-line comment saying why it must read configuration.
- Tests never reference an ADR in an expectation. Assert the behavior an ADR describes, never the document — not its existence, its `## Status` line, its headings, or its wording. An ADR is prose that gets amended, so a test that reads one fails on an edit that changed no behavior. The exception is a suite whose subject genuinely is the ADR corpus (`test/adr-hygiene.test.ts` lints the documents themselves).
- Keep comments short and to the point.
- Use American spelling in everything we author — UI strings, identifiers, file names, comments, ADRs, docs. Text and identifiers that come from the documented packages, and values already shipped to users such as the `cdk-docs:favourites` localStorage key, keep the spelling they have.
- Test names and comments describe the behavior under test in present tense. No issue numbers, no "regression for #N", no "previously this did X" — that history belongs in commit messages, PR descriptions, and ADRs. State the assertion's purpose instead: "the accessible name includes the level", not "guards #N".

### Testing Interactive Features

A PR that adds or changes an **interactive theme feature** must add or extend a
browser test in `test/e2e/`. This covers anything with client-side behavior a
user drives in the browser — the type-ahead symbol filter, the lazy API
sidebar, type hover tooltips, favorites, the feedback widget, the language
switcher, and site search. Unit tests of the docgen/build pipeline cannot
catch these regressions because they never load the rendered site; a misplaced
NavFilter and broken `/api/modules/` navigation both reached
`main` for exactly this reason.

This rule is **scoped to interactive features** — it does not apply to
docgen, build, or workflow changes, whose correct test is a Jest unit test.
Do not add an empty or trivial e2e spec just to satisfy the rule; if a change
has no interactive surface, a browser test is not expected.

Run the suite with `npx projen docs:e2e`. It builds a small fixture (a couple
of aws-cdk-lib services) rather than the full site, so it runs in under a
minute; the complete client-side data assets are kept intact, so features see
production-identical data. See the quality-gates ADR for details.

### Architecture Decision Records (ADRs)

Every technical decision must be recorded as an ADR in the `docs/adr/` directory. Name the file with the authoring date and a short kebab-case slug:

```
docs/adr/YYYY-MM-DD-short-title.md
```

Do **not** use a sequential number (`NNNN-...`): when several PRs are open at once they race for the same "next" number and collide when the second one merges. A date+slug name needs no coordination, never collides, and still sorts chronologically.

An ADR must include:
- **Status** — Proposed, Accepted, Deprecated, or Superseded
- **Context** — Why the decision is needed
- **Decision** — What was decided
- **Consequences** — Trade-offs and implications
