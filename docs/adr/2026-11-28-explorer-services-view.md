# Explorer Preview: The Services View

## Status

Accepted

## Context

Readers look for a construct by its AWS service: "the S3 bucket", "the SQS queue". With the Explorer preview on, the only way in has been the API view, which starts with the Framework section and then lists every service, each opening into resource groups and kind groups. A reader needs several clicks and some scrolling to reach a construct. The [rail ADR](./2026-11-26-explorer-preview-rail.md) shipped the rail with two views so that more views could follow; this is the first of them.

## Decision

The rail gets a third button, `Services`, first in the rail above `API` and `Favorites`. The Services view is one plain A to Z list of the AWS services, each row a caret, the service name and a count. It is the first, basic step: the filter settings menu, ranking of filter results and further views (Recent, Framework, Packages) are later work. The API and Favorites views do not change.

- **State.** `cdk-docs-explorer-view` accepts `services` besides `api` and `favorites`; the head script in `config.mts` repeats the three values, so `<html>` already carries the stored view before hydration. The tree renders as the Services view once the sidebar mounts; before that the sidebar shows its loading line in every view. The default view is still `api`. The rail button is a `<button>` with `aria-pressed` like the others, with a new glyph (`icons/services.svg`, a 2x2 grid of rounded squares); below 960px the Views button shows the same glyph and the text `Services` when this view is selected.
- **One rendering path.** `ApiSidebar.vue` renders the Services view as a tree derived from the data it already has: the skeleton's `Services` section and the per-service chunks. `servicesViewTree` in `api-sidebar.ts` returns the Services section's nodes, A to Z (case-insensitive), as the roots; an unloaded service keeps its skeleton node, so the existing chunk loading (on open, on a heading staying in view), the expansion store, the sticky headings, the filter and the density tokens all apply unchanged. The view fetches nothing of its own. The service nodes render at depth 1, where they sit under the API view's `Services` heading, so their rows indent as in the API view's tree.
- **Keys.** In the Services view a service's group key is its text (`S3`); in the API view it is `Services` + `S3`. Both live in the service style's expansion store without a clash, and the store's pruning keeps the Services view's keys (a service at the root, its kind groups under it) alongside the API view's. The Services view always uses the service style's expansion store; the package style never applies to it. Its per-route scroll memory is its own (`cdk-docs-sidebar-scroll:services`), since a position in this list points nowhere useful in the API view's trees.
- **The count in the skeleton.** A closed row shows the number of constructs of the service without loading its chunk, so docgen writes `count` on each node of the `Services` section when it splits the tree into skeleton and chunks (`splitSidebarChunks`). The rule is in `src/sidebar-rows.ts` and is shared by docgen and the client: a leaf at a service's top level is an overview when it has no `kind` (a readme) and a construct otherwise; a kind group's leaves are supporting types of that kind, except the `Constructs` kind group's; any other group (a resource, `General`) is walked with the same rule. So the count on a closed row always equals the rows under `Constructs` once the service is open (S3: 16 on the current data). While the filter is active a service's count is its matching rows.
- **An open service.** `serviceViewItems` lists, in this order and each part only when it has rows: `Overview`, a link to the overview page of the service's main module (the `aws-cdk-lib` module with the shortest page id, else the first overview row); `Modules`, one row per other overview page, named by module id without `aws-cdk-lib.` (a scoped package by its package name), in the code font, counting the type rows of that module; `Constructs`, every construct flat in the order of the generated tree, with its `L1`/`L2`/`L3` tag, a row without a tag keeping the tag's 28px so the names line up (as does every untagged row of the filtered list); `Types`, one closed kind group per kind the service has, merged across its resources, in the order Mixins, Facades, Traits, Events, Others (a kind the generator adds later follows them), rows A to Z, a kind group's `Type index` row (for types without a page of their own) last and outside the counts. Nothing is hidden. `Modules`, `Constructs` and `Types` are `part` nodes: a non-interactive sub-heading (`<p>`) over a `<ul>` named by it, at the part's own depth, its left edge at that depth's indent (14px at the default density).
- **Filter.** The existing filter box filters the Services list with the API view's filter rules (`filterSidebarTree`): with the filter active the derived tree lists each service's rows flat (overview, modules, constructs, then the types kind by kind) with no parts or kind groups, and `filterSidebarTree` keeps a service whose name matches with all of its rows, a service with matching rows with only those rows, and drops the rest. A term matches a row's text or its service's name and nothing else: the kind group names (`Others`, `Mixins`) and the resource and `General` group names of the API view's tree are not terms here, since the flat list has no such rows, so `others` finds nothing in this view while it keeps every `Others` group in the API view. Folds made while filtering are not saved, as in the API view.
- **EKS.** The generated tree already splits EKS into two sections, `EKS (legacy)` and `EKS V2` (`EKS_SECTIONS` in `src/docgen/sidebar.ts`); the shared `interfaces` and mixins types sit under `EKS (legacy)`. The Services view lists the two as plain rows under those names, sorted with the other services, each with its own overview, constructs, types and count. No client-side split rule is needed, and the names stay the sections' names, which the API view shows too.
- **Locate current page.** The control stays above the list. For a page in a service (`serviceForPath`: the service whose page-id stems own the path, as `chunkForPath`) it opens the service, selects the row and scrolls it to the middle of the sidebar. For a page in no service (a framework or `constructs` page) it is dimmed with `aria-disabled` (not `disabled`, so it keeps keyboard focus), its glyph and text at opacity 0.6 (the focus ring keeps full strength), `cursor: not-allowed`, activation does nothing, and a tooltip `This page is not in Services` tied by `aria-describedby` shows on hover, on keyboard focus and on activation (so a tap or Enter on the dimmed control shows why it does nothing); it stays while the pointer is over the control or the tooltip or the control has focus (each trigger is tracked on its own), and hides on Escape from anywhere, on the next tap elsewhere, and once no trigger holds (WCAG 1.4.13). The Escape's release is stopped too, so in the drawer it does not also close the drawer. The sidebar publishes the state through `jumpToCurrentUnavailable` in `sidebar-jump.ts` and it follows the route.
- **Ink.** A new token `--explorer-sub` (`#424650` light, `#a4a4ad` dark) colors the counts, sub-headings, kind group names, carets and row text of the Services view: 8.76:1 light and 7.48:1 dark on the sidebar surface (`--vp-c-bg-alt`), where `--vp-c-text-2` is 5.21:1 and 6.45:1. Service names keep `--vp-c-text-1`, the active row keeps `--vp-c-brand-2` on `--vp-c-brand-soft`, hover keeps `--vp-c-brand-1`. The API view keeps its colors.
- **Screen readers.** The list is a `nav` named `Services`. A service row is a button with `aria-expanded` and one accessible name that starts with the visible name: `S3, 16 constructs`, or `S3, 5 matches` while filtering; the visible count is part of the name (an unpainted comma follows the name and an unpainted noun follows the count). Kind group rows and module rows read the same way: `Others, 12 types`, `aws_s3_assets, 3 types`. Construct links keep the API view's names (`Bucket (L2 construct)`), and the current page has `aria-current="page"`. The dimmed Locate control is announced as dimmed with the tooltip text as its description.
- **Phones.** Below 960px the rail folds as on main and the Views button reads `Services`. The rows are sidebar drawer rows like the API view's and take the 44px height from `responsive.css`, as the [navbar ADR](./2026-10-15-navbar-footer-and-layout.md) records for drawer rows. A rejected alternative kept the desktop row height and reached 44px through a transparent overlay around each row, as the type page's chips do. That works for chips with a gap between them, not for rows stacked flush: every overlay would reach into its neighbors, and a tap near a row's edge would hit the wrong row.

## Consequences

- The skeleton grows by one small number per service. A later change to what counts as a construct row changes `src/sidebar-rows.ts` once, and the skeleton count and the open list move together; a test pins the two against the same fixture.
- The Services view and the API view share the service style's expansion store. Opening a service in one view does not open it in the other, since the keys differ, and a reader's folds in either view survive a reload.
- The rail ADR's "two view buttons" and its view values are extended by this record: three buttons, `cdk-docs-explorer-view` is `services`, `api` or `favorites`, anything else still meaning `api`. Tab inside the unfolded phone rail wraps between the first and the last button.
- The row text of the Services view is quieter than the API view's by design (`--explorer-sub` against `--vp-c-text-2`). Aligning the API view is a separate decision.
- On phones the Services view is as dense as the API view, not as dense as the desktop. A denser phone list would need a design that keeps the rows apart (a gap, or fewer rows per screen), which is a later decision.
- Removing the view later means deleting the rail entry, the glyph, `servicesViewTree` and `serviceViewItems` with their node fields (`part`, `count`, `moduleRow`), the `count` docgen writes, the `services-view` rules in `explorer-preview.css`, the token, the Locate `unavailable` state, and the `services` value in the state module and the head script.
