# Repository Conventions

## Status

Accepted

## Context

This repository is `private: true` and is never published to npm. Its only
artifact is a static documentation site. That single fact shapes several
repo-wide conventions — how dependencies are classified, how TypeScript runs,
and which upgrade PRs merge unattended — because the
usual npm-package meanings of those choices do not apply here. `package.json`
and the GitHub workflows are generated by projen from `.projenrc.ts`; hand-edits
are reverted by the next synth, so every convention below is expressed in
`.projenrc.ts`.

## Decision

### The package is ESM

`package.json` declares `type: module`; `tsconfig.json` and `test/tsconfig.json`
use `module` and `moduleResolution` of `NodeNext`. A dual CommonJS/ESM build was
rejected — nothing outside this repo consumes the package, so a second build
output buys nothing.

- `NodeNext` requires the extension the emitted JavaScript will have, so a
  relative source import names `./x.js` while the file on disk is `./x.ts`. Jest
  resolves against the source tree, so a `moduleNameMapper`
  (`^(\.{1,2}/.*)\.js$` → `$1`) strips the extension back off.
- Jest runs as ESM: `extensionsToTreatAsEsm` covers `.ts`/`.tsx`, the `ts-jest`
  transform sets `useESM`, and the test task passes
  `NODE_OPTIONS=--experimental-vm-modules`. This is what lets the repo depend on
  ESM-only packages (e.g. `htmlparser2`, now tracking its current major).
- `__dirname`/`__filename` do not exist in a module; code reads
  `import.meta.dirname` instead, setting a floor of Node 20.11.
- A JSON module exposes only a default export, so JSON imports destructure the
  key from a default import rather than importing it by name.
- The `jest` object is not a global under ESM, so the one suite that stubs a
  module imports it from `@jest/globals` (a declared devDependency).
- `scripts/*.cjs` stay CommonJS: they `require` each other, the pipeline runs
  them with `node` directly, and the suite loads them through `createRequire`.
  The `.cjs` extension is what keeps that working now that a bare `.js` here is a
  module. Each file states this in a comment.

### tsx is the TypeScript runner

The project-level `runner` is `TypeScriptRunner.tsx()`. One setting moves both
the docgen task entry points and the `.projenrc.ts` synth bootstrap, and projen
swaps the runtime dependency during synthesis. `tsx` is pinned by the caret
range projen generates. `ts-node` is gone from `package.json` and `.projen/`
(it was never a deliberate choice — projen injected it).

`tsx` has no type-checking mode, so there is no per-task opt-out to carry:
`compile` and eslint already check types, and synthesis keeps an explicit
`tsc --noEmit` pass over the projenrc tsconfig ahead of `tsx`.

### American spelling for everything this repository authors

Standardize on American spelling across prose, comments, identifiers, file
names, CSS class names, test names, and docs — `favorite`, `color`, `behavior`,
`center`, `gray`, `-ize`/`-ization`. The rule is recorded in `AGENTS.md` and
`CONTRIBUTING.md` and enforced by review, not by a lint suite (a spelling gate
would carry a pattern list and an exemption list that are never complete, giving
false comfort of a green build).

Two carve-outs, stated in the rule itself:

- API reference prose comes from jsii assemblies and package READMEs in
  `aws-cdk-lib` and `@aws-cdk/*-alpha`; it renders exactly as authored upstream.
- A string already written to a user's browser is data, not prose. The favorites
  localStorage keys keep their existing spelling — `cdk-docs:favourites` and
  `cdk-docs:favourites:collapsed` — exposed only as the values of the
  `STORAGE_KEY` and `COLLAPSED_STORAGE_KEY` constants. A migrating read of a
  renamed key was rejected: it buys a cosmetic key at the cost of a legacy path
  that lives forever where no reader sees it.

### Dependencies are classified by what the shipped site is made of

Because npm attaches no runtime meaning to the prod/dev split for an unpublished
repo, this repo gives it one: `dependencies` holds exactly the packages whose
code or assets ship in the built site, or that render its HTML — the VitePress
client runtime (`vitepress`, `vue`, `@vueuse/core`), the code-highlighter
(`shiki`, `@shikijs/engine-javascript`), math rendering
(`markdown-it-mathjax3`), search (`pagefind`, `vitepress-plugin-pagefind`), and
inlined icons (`lucide-static`). Everything else is a devDependency: docgen
tooling, the documented CDK packages (content sources — their prose ships, their
code does not), and all test, lint, CI, and release tooling.

A package belongs in `deps` iff its code or assets can be found in the built
site. This makes `license-checker --production` report attribution for what the
site is actually made of. Because docgen under `src/` now imports devDeps, the
eslint `import/no-extraneous-dependencies` rule allows devDeps in `src/**`; its
premise — that `src/` imports must be runtime-available to consumers — does not
hold for a repo whose only artifact is a static site.

### Recurring machine-authored dependency bumps auto-approve

Auto-approval (the `auto-approve` GitHub label, which is the only trust
boundary) covers recurring, machine-authored dependency bumps only:

- projen's `upgrade-main` deps-upgrade PR, labeled via
  `depsUpgradeOptions.workflowOptions.labels: ['auto-approve']` generated into
  `upgrade-main.yml`. `npx projen upgrade` only ever touches `package.json`, the
  lockfile, and `.projen/` bookkeeping, so no separate per-push verification is
  needed.
- the nightly CDK version-bump PR (see
  [versions and history](./2026-10-15-versions-and-history.md)).

Anything touching application or docgen logic stays human-approved, even when
machine-authored. The nightly module-list sync is deliberately *not* labeled: a
list change adds or deletes a whole module's pages, so a human merges it. No
Dependabot/Renovate config is adopted — projen's `upgrade-main` already provides
recurring npm upgrades and GitHub Action versions are pinned centrally in
`.projenrc.ts`. Approval only grants a review; merge stays gated by the required
`build` check that GitHub auto-merge waits on, so a broken upgrade cannot land
while CI is red (see [quality gates](./2026-10-15-quality-gates.md)).

### ADRs are excluded from the rendered site

ADRs are an internal engineering artifact for contributors, not for the site's
audience. Exclude them from the VitePress build via `srcExclude: ["adr/**"]` in
`docs/.vitepress/config.mts`, with no "Decision Records" nav entry or `/adr/`
sidebar section. `srcExclude` removes the pages at the source level, so no
`/adr/…` HTML is emitted and nothing downstream — sidebar, nav, or the Pagefind
index, which indexes built HTML — can surface them. The markdown files stay in
`docs/adr/`; the repo is the source of truth and ADRs are read on GitHub.
`test/adr-exclusion.test.ts` guards the exclusion.

## Consequences

- One TypeScript runtime (`tsx`) and one module system (ESM) across source,
  tests, and projen synthesis; ESM-only dependencies are no longer blocked.
- The prod/dev dependency split is a checkable statement of what runs in
  visitors' browsers; content sources and build tooling never creep into it.
- Routine `upgrade-main` and nightly version-bump PRs merge unattended once CI
  is green, reserving human review for behavior changes.
- Spelling is a review concern like the comment and test conventions, with the
  rule stating its own carve-outs so a legitimate British spelling in a shipped
  value or package-sourced prose needs no lookup.
- The built site contains no `/adr/…` pages; external links to previously
  published ADR pages 404, which is acceptable since ADRs were never the site's
  product surface.
